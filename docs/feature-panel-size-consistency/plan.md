# 패널 창 크기 통일 (클립보드 × 빠른 메모) — 계획

> 상태: 구현 완료 (2026-11-18, H=400 사용자 확정 — 코드·테스트 반영, 수동 검증 대기) | 작성: 2026-11-18
> 관련 문서: `docs/feature-scratchpad/plan.md` (600×320 결정), `docs/feature-clipboard-redesign/plan.md` (360×420 결정, O3 "미세 조정 예정") — 이 문서가 두 값의 **높이**를 대체한다.

## 1. 배경 (현재 동작)

### 1.1 현재 크기

| 패널 | 크기 | 내용 구성 | 표시 용량 |
|---|---|---|---|
| 클립보드 (`ClipboardPanelWindow`) | **360×420** 고정 | 헤더 30 + 목록(행 44px, 스크롤) | 목록 영역 = H−46 → 약 **8.1행** |
| 빠른 메모 (`ScratchPadWindow`) | **600×320** 고정 | 헤더 30 + TextBox(스크롤) | 텍스트 영역 = H−48 → 현재 **272px** |

### 1.2 배치 규칙 (`AnchoredPanelsLayout.PlacePanels`, 순수 함수)

- 단일 패널: 키보드 상/하반 기준 반대편, 수평 중앙.
- 복수 패널(총 너비 360+4+600=964 ≤ 작업 영역): 한 줄 나란히, 총 너비 기준 키보드 중심선 중앙. **아래 배치 = 상단 정렬 / 위 배치 = 하단 정렬**.
- 총 너비 초과: 폴백 — 클립보드는 rowSide(키보드 반대편), 나머지는 그 반대편에 개별 중앙.

### 1.3 문제

두 패널의 높이가 **100px** 차이(420 vs 320)라, 함께 열면 한쪽 끝만 맞는다:

- 아래 배치: 상단은 같은 선인데 클립보드 하단이 빠른 메모보다 100px 아래로 튀어나옴.
- 위 배치: 하단은 같은 선인데 클립보드 상단이 100px 위로 튀어나옴.

나란히 놓인 카드가 계단처럼 보임 → "창 크기"가 시나리오(각각/함께)에 따라 *실제로* 다른 모양으로 보이는 상태.

### 1.4 부수 발견: 크기가 2곳에 있고 한쪽은 죽어 있음

- `MainViewModel`의 `Register(id, order, width, height, ...)` 인자(360×420 / 600×320)는 `PanelEntry`에 저장되지만 **읽는 곳이 없다** — 레이아웃(`RelayoutAll`)은 실제 창 `_windows[id].Width/Height`(XAML 값)를 쓴다.
- 즉 크기의 실질 SSOT는 XAML의 `Width/Height`이고, Register 인자는 중복+사망 코드.

## 2. 목표

1. **모든 시나리오(각각 열기 / 함께 열기 / 재배치)에서 패널 크기가 동일** — "같은 키보드 위치면 항상 같은 자리" 원칙을 크기로 확장.
2. 함께 열 때 한 줄의 **상하 양 끝이 모두 일치**.
3. 내용 표시 용량 감소 없음 (명시된 트레이드오프 제외).
4. 새 설정 항목 없음 (최소 옵션 표면 — 사용자는 크기 조절 메뉴를 안 뜬다).

## 3. 설계

### 3.1 결정: 높이는 통일, 폭은 콘텐츠 기준 가변 유지

| 옵션 | 내용 | 평가 |
|---|---|---|
| **A. 높이만 통일 (추천)** | 두 패널 모두 표준 높이 H. 폭은 각자 (360/600) 유지 | 단순·예측 가능. 폭은 콘텐츠가 정함: 빠른 메모는 텍스트 편집이라 600 폭이 필요, 클립보드는 행 스캔이라 360이면 충분. 폭을 통일(B)하면 빠른 메모만 손해 |
| B. 높이+폭 모두 통일 (표준 패널 480×H 등) | 모든 패널 동일 치수 | 총 너비는 여전히 964(480+4+480)라 폴백 임계점 변화 없음 — 이득이 없고 빠른 메모가 좁아짐. 기각 |
| C. 함께 열 때만 동적 높이 맞춤 (둘 다 max=420, 닫으면 복원) | 각각 열 때는 각자 크기 | 열림/닫힘마다 창 리사이즈 → 내용 리플로우. "크기가 시나리오에 따라 변한다"는 이 계획이 없애려는 문제 자체. 예측 가능성 원칙 위반. 기각 |
| D. 크기 유지 + 시각적 정렬만 (예: 수직 중앙 정렬) | — | 근본 해결 아님, 키보드 가장자리와 사이가 비어 어색. 기각 |

### 3.2 표준 높이 H — 추천 **400** (대안 420)

H에 따른 숫자 (목록/텍스트 용량과 화면 적합성):

| H | 클립보드 표시 행 | 빠른 메모 텍스트 영역 | 768 노트북(작업 영역 720, 기본 키보드 320, 중앙-하단 배치) |
|---|---|---|---|
| 420 (현재 클립보드) | 8.1행 (변경 없음) | 372px (+100) | 위쪽 여유 396 < 420 → **24px 겹침** (마진 8px 넘어 → 마지막 행 일부 가림) |
| **400 (추천)** | 7.7행 (−0.4, 체감 동일) | 352px (+80) | 여유 396 < 400 → 4px 겹침 — **TextBox 하단 마진(12px) 안에서만**, 보이는 내용 무손실 |
| 320 (현재 빠른 메모) | 6.3행 (−1.8, 실감나는 감소) | 272px (변경 없음) | 여유 396 ≥ 320 → 안전 |

- 본머신(작업 영역 ~912)에서는 400/420 모두 여유 있음 — 검증 환경에서 겹침은 안 보임.
- 400의 이점: 짧은 화면(768 노트북)에서도 겹침이 **패딩 영역 안에만** 발생해 실제 내용이 가려지지 않음. 420은 클립보드 마지막 행을 일부 가림.
- 420을 원하면 (클립보드 행 수 보존, 빠른 메모 +100px) 단 768 노트북에서 행 일부 가림을 감수하는 트레이드오프다 — **사용자 선택** (§8).

### 3.3 시나리오 매트릭스 (H 통일 후)

| # | 시나리오 | 현재 | 통일 후 |
|---|---|---|---|

| S2 | 빠른 메모 단독, 키보드 하반부(기본 중앙-하단) → 위 배치 | 600×320 | 600×H — 텍스트 영역 +80px |

| S7 | 함께 열림 + 넓은 화면, 위 배치 | 하단만 일치 (100px 계단) | **상·하 양 끝 모두 일치** |

| S9 | 키보드 이동/리사이즈 (열려 있을 때) | RelayoutAll 재계산 | 동일 — 크기가 항상 일정 → 완전 결정론적 |
| S10 | 둘 중 하나 닫기 | 남은 패널 재중앙 | 동일 |
| S11 | 패널 드래그 | 위치만 임시 변경, 다음 재계산 시 복귀 (크기는 NoResize라 불변) | 동일 |
| S12 | 트레이 숨김/복원 | 함께 숨김·복원, 크기 불변 | 동일 |
| S13 | 멀티모니터 | 키보드 창이 있는 모니터의 작업 영역 사용 | 동일 — 크기는 고정 DIP 값이라 모니터와 무관 |

### 3.4 SSOT 정리 (동반 변경)

- `AnchoredPanelService.Register`에서 **width/height 인자 제거**, `PanelEntry` record도 해당 필드 제거 (사망 코드).
- 크기의 단일 출처 = 각 XAML의 `Width/Height`. 두 XAML에 "표준 패널 높이 — 서로 같은 값 유지" 교차 참조 주석.
- 레이아웃은 계속 실제 창 치수를 읽는다 (`RelayoutAll`) — 고정 크기라 항상 일치.

## 7. 수동 검증 체크리스트 (디버그 빌드, 자동완성 ON)

1. **클립보드 단독**: 헤더 버튼으로 열기 → 키보드 반대편 중앙에 360×400. 목록이 현재와 비슷한 행 수(약 8행)인지.
2. **빠른 메모 단독**: 열기 → 600×400, 텍스트 영역이 이전보다 넓어 보이는지 (스크롤 없이 더 많은 줄).
3. **둘 함께 열기** (핵심): 나란히 한 줄 — **상단·하단 양 끝이 같은 선인지** 확인. 키보드가 화면 상반부/하반부에 있을 때 각각 위/아래 배치로 확인.
4. **키보드 창 이동/스케일 변경** (열려 있는 동안) → 둘 다 재배치되고 높이는 그대로 유지.
5. **둘 중 하나 닫기** → 남은 쪽이 키보드 중앙으로 복귀.
6. **드래그 핸들** 드래그 후 다른 패널 열기/키보드 이동 → 위치는 계산 값으로 스냅백, 크기는 변하지 않음.
7. **기본 배치(중앙-하단)에서 겹침 확인**: 빠른 메모가 키보드 위쪽과 닿지 않는지 (본머신 작업 영역 ~912라 여유 있음 — 4px 마진 침범 여부만 육안).
8. 트레이로 숨김 후 복원 → 둘 다 같은 크기로 돌아옴.

## 8. 가정 · 오픈 질문

1. **H = 400 vs 420** — **400 확정 (사용자, 2026-11-18)**. 짧은 화면에서 겹침이 패딩 안에만, 클립보드 행 수 체감 동일.
2. **DPI 관찰 (본 계획 범위 밖)**: `app.manifest`에 `dpiAwareness`가 없어 DPI-unaware로 동작 — `GetWorkAreaFor`는 물리 픽셀을 반환하는데 WPF 좌표는 DIP라 100%가 아닌 스케일에서 클램프 계산이 어긋날 수 있는 *기존* 문제. 이번 높이 통일과 무관하게 존재하며, 발견 시 별도 작업으로 처리.
3. **큰 스케일 키보드 + 짧은 화면의 세로 오버플로** (S4): 현재도 클램프로 겹치는 기존 동작. 후속 옵션으로 "한쪽에 안 들면 반대편으로" 플립 규칙을 `PlacePanels`에 추가할 수 있으나, 이번 계획에는 포함하지 않음.
4. **Register 인자 제거**: 사망 코드라 제거를 권장하지만, API 시그니처 변경이라 원하면 "인자는 두고 XAML과 일치하는지 주석만"도 가능 — 기본은 제거.
5. 향후 새 앵커 패널(AI 패널 등)이 추가되면 **표준 높이 H를 그대로 채택**하는 관례로 유지 (한 줄 정렬이 자동으로 성립).
