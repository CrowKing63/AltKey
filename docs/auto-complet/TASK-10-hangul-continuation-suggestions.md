# TASK-10 — 조합 중 한글 음절의 이어쓰기 후보 제안

> 상태: 구현 완료
> 범위: 한국어 자동완성 제안 검색만 확장했다. 한글 조합기와 실제 입력 동작은 변경하지 않았다.

## 목표

사용자가 한글 음절을 입력하는 중 마지막 음절에 이어 붙일 수 있는 종성 또는 겹중성을 포함한 단어도 제안한다. 또한 완성된 앞부분 뒤에 다음 음절의 초성만 입력한 상태도 처리한다. 예를 들어 `고` 입력 시 사용자 사전의 `괴물`, `괜찮을`을, `깃ㅎ` 입력 시 `깃허브`를 후보로 노출한다. 다중 음절 입력에서는 앞부분을 고정하고 마지막으로 입력 중인 음절만 확장 대상으로 삼는다.

## 배경 (현재 레포 기준)

- `AltKey/Services/InputLanguage/KoreanInputModule.cs:97-118`는 키 입력을 `_composer.Feed`로 처리한 뒤 현재 조합 문자열을 `KoreanDictionary.GetSuggestions`에 전달한다. 백스페이스 경로도 같은 사전을 호출한다 (`:182-210`).
- `AltKey/Services/KoreanDictionary.cs:54-79`는 초성 한 글자일 때 별도 초성 검색을 하고, 완성된 입력은 prefix로 검색한다. 완성 음절 뒤에 초성 자모만 붙은 상태(예: `깃ㅎ`)는 다음 음절 초성 기준의 검색 경로를 추가했다.
- `KoreanDictionary.GetSuggestions(prefix, prevWord, count)` (`KoreanDictionary.cs:154-199`)가 기본 후보에 bigram 가산·삽입을 적용한다. 확장 검색은 기본 후보 생성 단계에서 이루어져야 문맥 검색에도 동일하게 적용된다.
- 사용자 사전 검색은 `WordFrequencyStore.GetSuggestions` (`AltKey/Services/WordFrequencyStore.cs:127-141`)에서 빈도 내림차순으로 수행된다. 초성 검색도 별도 메서드다 (`:143-157`).
- 관련 테스트는 `AltKey.Tests/InputLanguage/KoreanDictionaryTests.cs`에 있다. 현재 `GetSuggestions_with_complete_syllable_prefix_unchanged`는 `가` 후보가 전부 `가`로 시작한다고 고정하고 있으므로, 확장 후보를 허용하도록 검증 의도를 갱신해야 한다.
- `AltKey.Tests/InputLanguage/TestHelpers.cs:36-80`의 `WordFrequencyStoreInMemory`는 기반 메서드를 `new`로 숨기고 자체 저장소를 사용한다. 기반 `WordFrequencyStore`의 새 검색 메서드를 `KoreanDictionary`에서 호출하면 테스트 데이터가 보이지 않을 수 있으므로, 테스트 저장소와 실제 저장소의 동작 계약을 함께 맞춰야 한다.
- `docs/auto-complet/CORE-LOGIC-PROTECTION.md:41-58`은 `HangulComposer` 내부 조합 알고리즘을 동결한다. 이 작업은 `KoreanDictionary`의 후보 검색·병합만 변경하며 `HangulComposer.Feed`, `Backspace`, 조합 상태나 `KoreanInputModule` 입력 파이프라인은 바꾸지 않는다.

## 결정

1. 확장은 **마지막 음절에만** 적용한다. 입력 `가나`에서 `가`는 고정하고 `나`만 후보 음절로 확장한다. 앞쪽 음절을 다른 음절로 바꾸거나 초성 검색 의미를 바꾸지 않는다.
2. 확장 검색이 적용되는 경우 기준 후보와 확장 후보를 사용자 빈도순으로 통합한다. 빈도가 같으면 정확 prefix 후보를 먼저 노출하고, 그 다음 단어 순으로 안정 정렬한다.
3. 내장 사전에는 사용자 학습 빈도가 없으므로 사용자 후보 뒤에 배치한다. 내장 후보끼리는 정확 prefix를 확장 후보보다 먼저 두고 기존 리소스 순서를 유지한다.
4. 확장 후보는 `HangulComposer`가 현재 조합 음절에서 이어서 만들 수 있는 결과로 제한한다. 현재 음절에 종성을 더하는 경우, 중성을 결합해 겹중성을 만드는 경우, 겹받침 뒤 모음 입력으로 겹받침을 분리해 다음 음절을 시작하는 경우를 포함한다. 임의의 모음 교체나 다른 초성은 허용하지 않는다.
5. 초성 입력(예: `ㄱ`) 동작과 두 음절 이상 prefix의 앞부분 일치 규칙은 변경하지 않는다.
6. 마지막 입력이 완성 음절이 아니라 초성 자모이고 앞에 완성 음절이 있을 때, 그 초성을 바로 다음 음절의 초성과 비교한다. 앞에 입력된 문자열은 바꾸지 않는다.
7. 기본적으로 입력보다 긴 단어만 제안한다. 단, 입력이 완성된 한 음절이고 사용자 사전에 정확히 같은 한 음절 단어가 저장돼 있으면 해당 단어도 제안한다.

## 작업

### 1. 조합 규칙의 근거를 확인한다

- `AltKey/Services/HangulComposer.cs`와 `AltKey.Tests/InputLanguage/HangulComposerTests.cs`에서 겹중성 및 종성 조합의 실제 지원 범위와 테스트 사례를 확인한다.
- 후보 검색에 필요한 것은 “현재 음절에서 허용되는 다음 음절 후보”의 집합이다. `HangulComposer`의 내부 상태를 조회하거나 조합기를 실행해 상태를 변경하는 방식은 사용하지 않는다.
- 문자 분해·재조합은 이미 존재하는 공용 유틸리티가 있는지 검색한다. 없으면 새 순수 함수의 설계를 먼저 검토하고, 음절 코드포인트를 손으로 추산하지 않는다. 구현 시 프로젝트의 Hangul 계산 도구/기존 검증된 조합 로직을 ground truth로 삼는다.

### 2. 후보 검색 API를 설계한다

- `WordFrequencyStore`에 기준 prefix로 시작하는 후보와, 정해진 시작 음절 집합에 해당하는 후보를 빈도순으로 얻는 기능이 필요하다.
- 기존 검색 계약(빈 prefix 처리, `Length > prefix.Length`, 대소문자 비교, 정렬)을 보존한다. 새 검색은 대상 첫 음절을 명시적으로 제한하고, 결과 수를 호출자가 제어할 수 있어야 한다.
- `WordFrequencyStoreInMemory`도 같은 API를 제공하여 테스트가 실제 저장소와 같은 검색 의미를 갖게 한다. 테스트 헬퍼의 `new` 메서드 숨김 구조를 고려해 다형성에 의존한다고 가정하지 않는다.
- 실제 저장소와 테스트 저장소 사이의 새 API/정렬/필터 규칙을 테스트로 고정한다.

### 3. 한국어 사전의 병합을 구현한다

- `KoreanDictionary.GetSuggestions(prefix, count)`에서 기존 기준 후보를 먼저 얻는다.
- `prefix` 끝이 완성 한글 음절일 때만 마지막 음절을 확장한다. 초성 자모 prefix나 비한글 문자는 기존 경로로 처리한다.
- 앞 prefix(마지막 음절 제외)를 고정하고 마지막 음절의 허용 변형을 붙여, 각 변형을 첫 음절로 갖는 후보를 수집한다.
- 동일 후보가 여러 변형·사전 경로에서 중복 수집되지 않게 ordinal 기준으로 제거한다.
- 사용자 후보는 확장 여부와 관계없이 빈도순으로 합쳐 반환한다. 빈도가 같으면 정확 prefix 후보를 앞세우고, 내장 사전은 그 뒤에서 기존 순위를 따른다. 중복 제거·`count` 상한·bigram 처리 순서를 테스트로 확인한다.
- `count`를 채우면 더 검색하지 않거나 최종 단계에서 잘라 반환한다. 기본 검색과 확장 검색이 각각 `count`개를 반환해 최종 결과가 `count`를 넘는 일이 없어야 한다.
- `GetSuggestions(prefix, prevWord, count)`의 bigram 가산/삽입은 이 결과를 기반으로 그대로 동작해야 한다. prefix와 일치하지 않는 bigram 후보를 무조건 추가하는 기존 정책은 이 작업에서 바꾸지 않는다.

### 4. 테스트를 기능별로 보강한다

파일: `AltKey.Tests/InputLanguage/KoreanDictionaryTests.cs` 및 필요한 경우 `AltKey.Tests/InputLanguage/WordFrequencyStoreTests.cs` (파일 존재 여부와 기존 테스트 구조를 구현 전에 확인)

필수 사례:

1. 사용자 사전에 `괴물`, `괜찮을`을 넣고 `고` 검색에서 두 단어가 모두 후보가 된다.
2. 기준 후보와 확장 후보는 사용자 빈도순으로 통합하고, 빈도가 같을 때는 정확 prefix 후보를 먼저 둔다.
3. 종성 확장 사례: `가`에서 `각...`, `간...` 후보가 가능하고, 현재 기준 `가...` 후보는 유지된다.
4. 다중 음절 사례: `가나`에서 앞 음절 `가`는 유지하고 마지막 음절 `나`에서 파생되는 후보만 포함한다. 앞부분이 다른 단어는 제외한다.
5. 허용되지 않는 중성/초성 후보는 제외된다. 예: `고` 입력에서 규칙상 이어질 수 없는 임의의 다른 모음 음절이나 다른 초성으로 시작하는 단어를 반환하지 않는다.
6. 기준 후보와 확장 후보 사이의 중복은 한 번만 반환된다.
7. 후보 수는 `count`를 넘지 않으며, 결과가 적을 때 예외 없이 가능한 후보만 반환한다.
8. 완성 음절 뒤에 초성 자모 하나가 입력된 경우, 앞부분은 ordinal로 고정하고 다음 음절의 초성만 일치시킨다. `깃ㅎ`는 `깃허브`와 일치하고, `깃가…` 및 다른 앞부분 단어는 제외한다.
9. 초성 입력 `ㄱ`과 다중 음절 접두사의 기존 의미가 유지된다.
10. bigram 문맥 경로에서 확장 후보가 기본 후보에 포함된 경우 기존 가산·정렬·상한이 유지된다.
11. 실제 저장소와 인메모리 테스트 저장소가 같은 확장 검색 필터와 빈도 정렬을 보인다.

테스트 주석은 무엇을 검증하는지만 한국어로 쓴다. 테스트 파일은 400줄을 넘기지 말고, 초과할 우려가 있으면 별도 기능 파일로 분리한다.

### 5. 빌드와 회귀 검증

## 검증 기준 (완료 조건)

- `고` 검색에서 사용자 사전의 `괴물`, `괜찮을`이 각각 검색되는 테스트가 통과한다.
- `가` 및 `가나` 경로에서 종성/겹중성 확장이 의도한 마지막 음절에만 적용된다.
- 기준 후보 우선, 사용자 사전 우선, 중복 제거, 빈도 정렬, 최대 반환 수, bigram 동작이 테스트로 보호된다.
- 초성 입력과 다중 음절 접두사의 기존 동작이 유지된다.
- 사용자 사전에 저장된 한 음절 단어는 초성 후보(예: `ㄱ`에서 `가`)에 나타나고, 첫 완성 음절(예: `가`)에서도 exact-match 후보로 계속 나타난다.
- HangulComposer 보호 영역을 수정하지 않고 전체 테스트와 지정 빌드가 통과한다.

## 구현 확인 기록

- `HangulComposer`의 공개 입력 경로를 이용해 현재 음절에 실제로 결합 가능한 중성과 종성을 생성했다. 조합기 내부 알고리즘은 변경하지 않았다.
- 한글 음절은 Unicode 정규 분해로 초성·중성·종성을 읽고, 종성 매핑은 조합기가 만든 표본으로 확인한다. 코드는 음절 코드포인트를 수동 조합하지 않는다.
- 사용자 단어 저장소 테스트 구현은 기반 저장소 메서드를 가려 실제 사전 호출 경로를 검증하지 못했으므로, 관련 메서드를 virtual/override로 연결했다.
- 단일 종성은 다음 모음 입력으로 그 종성이 다음 음절의 초성이 되는 경우(예: `붑`→`부분이`)를 검색한다. 겹받침은 입력 자모를 `HangulComposer`로 재현해 모음 입력 시 분리되는 결과(예: `얹`→`언제`)를 검색하고, `업무`·`얼굴` 같은 다른 종성 후보는 제외한다.
- 검증: 한국어 사전 테스트 21개 통과, 전체 테스트 244개 통과, `AltKey.Tools` 빌드 경고 0·오류 0.
