# 09 — 모델 적합성 검증 (laya-ko: 한국어·용도·비용)

> 이 문서는 1~8번 구현을 **시작하기 전에** 통과해야 하는 게이트이다. laya-ko가 AltKey의 "다음 단어 재평가" 용도에 실제로 쓸 만한지, 그리고 그 비용이 감당 가능한지를 근거로 판단한다. **09번 PoC가 통과하지 못하면 1~8번은 시행하지 않는다**(기존 자동완성 유지).

## 결론 (일단 요약)
- **기술적으로 실행은 가능**: ONNX + 토크나이저 + 검증 벡터(`golden.json`)가 공개되어 있고, CPU ~30ms로 150ms 타임아웃 안에 들어온다.
- **그러나 이 용도로는 검증되지 않았다**: laya-ko는 "문서를 주어진 범주로 분류"하는 결정 모델이지, "다음 단어를 고르는" 언어 모델이 아니다. 한국어 정확도는 독립 테스트에서 약한 편이다.
- **비용이 크다**: 다운로드 ~1.23GB, 상주 RAM ~1.2GB. "초소형"이 아니다. 키보드 앱에 이 비용을 지울 수 있는지를 사용자에게 명확히 알리고 동의받아야 한다.
- **결정**: PoC 게이트(아래)로 판단. 통과 시 1~8번 진행, 실패 시 AI 기능 미출시 + 모델 재선정.

## 근거

### 1. 용도 불일치 (가장 중요)
- laya-ko = mmBERT-base 인코더 + 결정 헤더(322M 파라미터), **비생성형**. `choice`/`score`/`noul` 세 가지 질문을 받아 각 옵션에 확률을 매긴다.
- 학습 데이터: KLUE(NLI·주제·STS·관계) 102,665건 + 영어 replay. 모두 **문서 단위 분류** 과제.
- AltKey가 원하는 작업("문장 prefix + 후보 단어 집합 → 다음 단어로 가장 자연스러운 후보 선별")은 **다음 단어 예측/언어 모델링** 과제로, laya-ko가 학습한 적 없는 형태다. `choice` 타입으로 "후보 중 맞는 것 고르기"를 프레이밍할 수는 있으나, 이 특정 작업에 대해 좋은지라는 증거가 없다.
- 모델 카드 스스로: "No world knowledge", "KMMLU 0.298 (chance 0.250)". 단어를 '아는' 모델이 아니라 앞의 텍스트를 '판단'하는 모델이다.

### 2. 한국어 정확도 (독립 테스트)
- laya-ko 공식 벤치마크(KLUE)는 학습한 과제가 NLI 81%, YNAT 82%, RE 70.5%로 꽤 높다. 그러나 이는 **학습한 분류 과제**의 수치다.
- 독립 비교(eazler.com, MASSIVE 1.1 기반 18분류): `laya:multilingual`(laya-ko의 베이스)이 **한국어 47~48%** (영어 56.9%, 무작위 5.6%). 즉 반은 틀린다.
- 같은 테스트에서 Qwen3.5 기반 ~0.8B 디코더 모델은 한국어 71~81%였으나 **요청당 1~2초**(자동완성에는 너무 느림).
- 결론: laya-ko의 한국어를 "학습한 분류"로는 쓸 만하지만, "다음 단어 고르기"라는 학습하지 않은 과제로는 불확실하며, 한국어 이해 자체도 평균 이하일 수 있다.

### 3. 비용 (다운로드·메모리)
- 파일 구성(2nugu/laya-ko `onnx/`):

  | 파일 | 크기 | SHA-256(LFS oid) |
  |---|---:|---|
  | model.onnx | 2,290,168 B (2.3 MB) | `88e98635e750a690ddc1301910b9452570604e514264903cd66cbfd4932338ff` |
  | model.onnx.data | 1,286,864,896 B (1.29 GB) | `e778e44657cbcad44c462f70bf810d384d92574f76e5e732afee1c8559e9dad7` |
  | tokenizer.json | 34,363,188 B (34.4 MB) | `609d8f4c067cd3950f88594c5a802616cea245823836ef5848ee4fc40aab5b6f` |
  | laya_runtime.json | 937 B | (소형 — 구현 시 계산) |
  | golden.json | 64,977 B | (소형 — 포트 검증용) |

- **총 다운로드 ≈ 1.23 GB**. fp32라 상주 RAM도 ~1.2GB. int8 동적 양자화는 310MB로 줄지만 정확도 -9pp로 "값 안 됨"(repo 명시).
- 키보드 앱에 1.2GB 다운로드 + 1.2GB RAM은 큰 부담이다. "별도 설치 없이"라는 원칙과도 사실상 충돌한다.

### 4. 성능 (긍정)
- CPU fp32: **28~48 ms/item**(batch 16). 옵션 수에 비례. 150ms 타임아웃 안에 여유 있음.
- 토크나이저(BPE, 34MB) + 시퀀스 구성(C# 포트)이 추가 지연으로 붙는다 — PoC에서 실측 필요.

### 5. 토크나이저·시퀀스 (확정됨)
- `tokenizer.json`(34MB BPE)가 repo에 있다. 특수 토큰: `<bos>/<eos>/<mask>/<pad>`.
- 시퀀스 구성 알고리즘은 `docs/ONNX.md`의 8단계 규칙으로 확정(03번에 전수).
- `golden.json`(13케이스)이 토큰 id·마커 위치·확률까지 기대값으로 제공해 **C# 포트를 검증**할 수 있다.

## 결정: PoC 게이트
1~8번 구현 전에 아래 PoC를 먼저 수행한다. 목적은 "laya-ko가 기존 baseline보다 다음 단어 재평가에서 실제로 이기는지"를 AltKey 실데이터로 판단하는 것.

### PoC 범위 (C# 불필요 — Python 하네스로 충분)
1. AltKey의 실제 (context, 후보집합) 쌍 N개(예: 300~500)를 수집. (사전+bigram 데이터에서 구성, 또는 타이핑 로그)
2. 각 쌍에 대해 laya-ko `choice`로 "이 문장의 다음 단어로 가장 자연스러운 것을 고르세요" 질문 + 후보 옵션을 주어 상위 N개 랭킹 산출.
3. 기존 baseline(빈도+Bigram) 랭킹과 비교.

### 통과 기준 (미리 고정)
- **랭킹 품질**: MRR@3 또는 top-1 적중률이 baseline 대비 유의하게 개선(예: MRR@3 +X pp, 또는 top-1 적중률 ≥ Y%). 임계값은 PoC 시작 전 숫자로 확정.
- **지연**: 토크나이징 포함 1회 요청이 150ms 이내(실측).
- **비용 수용**: 1.23GB 다운로드 + 1.2GB RAM을 "수용 가능한가"를 기획 판단으로 명시. (사용자 opt-in + 크기 경고 전제)

### 실패 시
- 1~8번 **미시행**. 기존 자동완성(빈도+Bigram) 유지.
- 모델 재선정 아래 대안 검토.

## 대안 (PoC 실패 또는 품질 부족 시)
1. **laya-ko를 AltKey 다음-단어 데이터로 fine-tuning**: repo에 학습 파이프라인 존재(RTX PRO 6000 기준 ~19분). PoC가 "방향은 맞지만 미조정"이면 이 경로로 전진. 1차에서 "향후"로 밀어둔 것을 당겨올 수 있다.
2. **더 작은 한국어 인코더**(KoreALBERT 12M, ko-BERT 계열)를 후보 점수 과제로 fine-tune: 다운로드/메모리 부담 낮음. 소스+학습 필요.
3. **Qwen3.5 ~0.8B 디코더**: 한국어 정확도 우위(71~81%)이나 요청당 1~2초 → 키 입력당 실행은 비현실적. 배치/캐시에 의존해야 함.
4. **신경 모델 없음**: n-gram/trigram + 빈도 강화. 다운로드·메모리 제로, 즉시. AI가 이겨야 할 baseline 자체.
