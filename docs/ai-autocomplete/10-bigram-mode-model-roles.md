# 10 — 바이그램 모드 × 결정 모델 역할 가능성 검증

> **이 문서의 역할**: **구현 지시서가 아니다.** 결정 모델(laya-ko)이 바이그램 모드에서 "꼬리 채움 + 노이즈 제거"만 맡는 새 역할 프레임과, 사용자가 스스로 판정할 수 있는 PoC 게이트·테스트 결과 정리 방법론을 정의한다.
>
> **09와의 관계**: `09-model-viability.md`의 최종 결정(AI 자동완성 rerank 포기)은 **무효화되지 않는다.** 그 결정의 킬러 게이트(30ms 지연, 상위 포지션 일관성)는 "매 키스트로크 rerank" 프레임에 특화된 것이었다. 이 문서는 두 게이트가 구조적으로 바뀐 *새 역할 프레임*에서의 재검토이며, 이 PoC가 대체하기 전까지 09의 결정이 유효하다.

## 1. 왜 재검토하는가 — 09와 무엇이 달라졌는가

| 09의 킬러 게이트 | 09의 프레임 (매 키스트로크 rerank) | 본 문서의 역할 프레임 |
|---|---|---|
| 지연 p50 < 30ms | 후크 지점 = 조합 중 `SuggestionsChanged` (매 키 입력) | 후크 지점 = **단어 수락 직후** (비동기 윈도우, 사용자가 스캔하기 전) → 100~300ms 허용 |
| top-1 일관성 ("한 번의 어긋남도 신뢰를 깨므로") | 모델 출력이 **상위 포지션을 소유** | 모델 출력이 **bigram 히트보다 위로 올 수 없음** (구조적 보장) → miss = 꼬리 노이즈 / 저신뢰 쌍 매장 |
| 환각 위험 | 제약된 점수만 (생성 안 함) | 동일 — 고정 후보 풀, 생성 없음 |

laya-ko의 Qwen(디코더) 대비 비용 메리트: 자기회귀 디코딩·KV 캐시 없이 **단일 forward pass**, CPU 전용. small N(옵션 5~8개, ~120~160토큰) 기준 fp32 **~74~100ms** (09 실측).

## 2. 역할 정의

### 역할 A — Filler Scorer (희박 바 채움)
- **트리거**: `AcceptSuggestion`/`AcceptBigramSuggestion` 이후 bigram 히트가 3개 미만일 때. (현재: 히트 있으면 bigram 목록만, 없으면 빈 바로 초기화 — `AutoCompleteService.cs:97~101`)
- **후보 풀**: 알려진 어휘만 — 사용자 빈도 스토어 + 내장 사전 상위 5~8개. 생성 없음 → 환각 구조적으로 불가능.
- **문맥**: 최근 3~5단어 (prevWord 하나만이 아님 — 바이그램 모드의 1단어 문맥이 구조적 약점).
- **배치**: bigram 히트보다 **아래**, 2~3개로 캡.
- **fail-safe**: 타임아웃/오류 → 빈도 풀 원본. **절대 빈 바로 안 감.**
- **품질 기준**: "합리적 필러 ≥ 빈도 폴백" — top-1 정확도가 아님.

### 역할 B — Pair Verifier / Demoter (저count 쌍 노이즈 제거)
- **트리거**: count ≤ 2인 bigram 히트. `GetNexts`에 최소 count 임계가 없음(`BigramFrequencyStore.cs:131~136`) → count=1의 우연한 인접 쌍도 그 prev의 후보가 적으면 바에 그대로 노출됨.
- **질문 형식**: "C가 W 뒤에 자연스러운가?" — 선별이 아니라 **판단** (NLI 계열, laya-ko가 학습한 과제족).
- **동작**: 실패 쌍을 꼬리로 **디모트만**. 승격 절대 안 함.
- **fail-safe**: 오류 → 원본 순서 유지.
- **miss의 비용**: 타당한 저신뢰 쌍 매장 — 회복 가능(다시 입력하면 count가 재_accumulate).

## 3. 이 설계가 laya-ko의 문서화된 약점을 무력화하는 이유

| 09의 실패 근거 | 이 프레임에서의 상태 |
|---|---|
| 지연 74~204ms (30ms 게이트) | 키 입력 경로 아님 — 비동기 윈도우, small N ~74~100ms. 게이트 소멸 |
| top-1 적중 30% | 상위 포지션 소유 불가(구조적 보장). miss = 꼬리 노이즈로 강등 |
| 일관성 한계 ("한 번의 어긋남") | bigram-primary + demote-only. miss = 저신뢰 쌍 매장/꼬리 노이즈 |
| "No world knowledge"·한국어 약함 (독립 테스트 47~48%) | 단어 '알기' 불필요 — 고정 풀의 표면 판단만 (NLI 유사 과제) |
| int8 정확도 훼손 (확률 오차 15.7%) | RAM 허용이면 fp32 유지. 디모터는 fp32 권장 |

## 4. honest한 한계 (이 설계로도 못 넘는 것)

- **지식 생성 불가**: 문맥이 진짜로 새로워서 빈도 풀에 관련 단어가 없으면, 필러는 "꾸민 빈도 목록"에 그친다. 모델의 영비용 trigram/빈도 베이스라인 대비 가치는 좁은 조각(문맥적·저빈도 단어)뿐이다.
- **한국어 판단력 47~48%**: 디모터 정밀도가 mediocre할 수 있다 — 좋은 count=1 쌍을 매장하는 비용이 실제로 발생한다. 게이트 2가 존재하는 이유다.
- **비용 정당화 부담**: 그 좁은 조각에서 영비용 베이스라인에 *명백히* 이기지 못하면, 다운로드/RAM 비용은 절대 품질과 무관하게 정당화되지 않는다.

## 5. PoC 게이트 정의 (실행 전 고정)

> 임계값은 PoC 시작 **전**에 숫자로 고정한다 (09와 동일 원칙). 결과를 보고 바뀌면 판정 무효.

### 게이트 0 — 지연 (객관적, 사용자 판단 불요)
- **방법**: small N(옵션 5~8개, ~120~160토큰) choice 추론 p50, 본머신 fp32.
- **도구**: Python onnxruntime CPU EP 하네스 (원본 `~/.hermes/cache/scratch/laya-poc/` — 스래시 정리됐으면 09 PoC 절차로 재작성. C# 불필요).
- **게이트**: p50 < **150ms**
- **실패 → 즉시 중단**: 역할 A·B 모두 포기, 09 결정 유지.

### 게이트 1 — Filler (역할 A)
- **데이터셋**: N=**30**개 실 희박 문맥 (bigram 히트 < 3)
  - prev 단어: `user-bigrams.ko.json`에서 nexts가 3개 미만인 항목
  - context: 그 prev 단어로 자연스럽게 이끄는 앞선 2~4단어 **수동 구성** (AltKey에 문장 단위 로그가 없어 반자동 구성 — honest한 제약)
  - pool: `user-words.ko.json` + 내장 `ko-words.txt` 상위 5~8개 (bigram 히트 제외)
- **케이스당**: 모델 top-3 순서 vs 베이스라인(빈도) top-3 순서. 사용자가 각 포지션을 2/1/0로 평가.
- **집계**: 90개 평가 총점 (max 180)
- **게이트** (모두 통과해야 PASS):
  - (a) 모델 총점 ≥ 베이스라인 총점 (못 지기)
  - (b) 모델 0점 개수 ≤ 베이스라인 0점 개수 (miss 증가 없음)
  - (c) 모델 총점 − 베이스라인 총점 ≥ **+15** (가치 조각에서의 명백한 우위 — 비용 정당화 조건)

### 게이트 2 — Demoter (역할 B)
- **데이터셋**: N=**60**개 저count 쌍 (count ≤ 2), `user-bigrams.ko.json`에서 추출
  - 라벨: 사용자가 "W → C"를 읽고 good/bad 이분 판단 (~20분)
- **지표**:
  - Precision = (디모트 ∩ bad) / 디모트 — 매장 비용
  - Recall = (디모트 ∩ bad) / bad — 노이즈 제거량 (참고용)
- **게이트**: precision ≥ **80%**
- **fail-safe 검증** (자동): 모델 오류/타임아웃 → 원본 순서 유지 확인 (사용자 판단 불요)

### 판정 경로
| 결과 | 판정 |
|---|---|
| 게이트 0 실패 | 전부 포기 — 09 결정 유지 |
| 게이트 1 + 2 통과 | 두 역할 모두 가능 → 새 구현 기획 문서 시리즈 (본 문서 범위 밖) |
| 하나만 통과 | 해당 역할만 (예: demoter-only) |
| 둘 다 실패 | baseline 유지, 모델 포기 |

## 6. 테스트 결과 정리 방법론 (사용자 자가 평가 절차)

### 6.1 파일 레이아웃

### 6.2 데이터 스키마

**contexts.json** (filler 데이터셋):
```json
[
  {
    "id": 1,
    "context": ["오늘", "날씨가", "좋네요"],
    "bigram_hits": ["많이"],
    "pool": ["조용히", "바빠요", "괜찮아요", "좋아요", "천천히"],
    "baseline_order": ["바빠요", "괜찮아요", "좋아요"],
    "model_order": ["괜찮아요", "조용히", "바빠요"]
  }
]
```
- `context`: 최근 3~5단어 (prev 단어 포함) — 모델 입력
- `pool`: 알려진 어휘 후보 (bigram 히트 제외)
- `baseline_order`: 빈도 top 3 (영비용 베이스라인)
- `model_order`: 모델 top 3

**ratings.csv** (사용자 평가 시트 — raw 데이터):
```csv
case_id,position,source,item,rating
1,1,model,괜찮아요,2
1,1,baseline,바빠요,1
1,2,model,조용히,1
...
```
- `rating`: 2=자연스러움 / 1=허용 가능하나 약함 / 0=명백히 어긋남

**pairs.json** (demoter 데이터셋):
```json
[
  { "id": 1, "prev": "감사합니다", "next": "네", "count": 1, "label": "good" },
  { "id": 2, "prev": "밥", "next": "바다", "count": 1, "label": "bad" }
]
```

### 6.3 평가·라벨링 가이드
- **filler 평가**: 각 항목을 "이 문장에서 다음에 이 단어가 자연스럽게 올 것인가?"로만 판단한다. 모델/베이스라인을 나란히 비교하며 평가하지 않는다 (앵커링 방지 — 각각 독립 평가).
  - 2 = 자연스러움 / 1 = 불가능은 아니지만 약함 / 0 = 명백히 어긋남
- **demoter 라벨**: "W → C"를 읽고 "C가 W 뒤에 자연스러운가?"로만 판단한다. 빈도나 개인 사용 습도는 생각하지 않는다.

### 6.5 실행 순서와 중단 조건
1. **게이트 0 먼저** (객관적, 저렴). 실패 → 중단, 사용자 평가 불필요.
2. **게이트 1**: 30케이스 × 6평가 = 180개 판단 (~30~45분)
3. **게이트 2**: 60 라벨 + 자동 precision/recall (~20분)
- 각 게이트는 이진 PASS/FAIL. **raw 데이터를 먼저, 집계를 나중에** 기록해 판정을 재계산·감사할 수 있게 한다.

### 6.6 기록 규칙
- raw 케이스 데이터가 집계보다 우선 — 재계산·감사 가능해야 함
- summary 헤더에 모델 버전, 양자화(fp32/int8), 머신 스펙 필수
- 게이트가 경계면 어떤 케이스가 판정을 끌었는지(케이스별 테이블) 기록
